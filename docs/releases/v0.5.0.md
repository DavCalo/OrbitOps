# OrbitOps v0.5.0 — unified session inspection and operational evidence

OrbitOps v0.5.0 turns the previously separate telemetry, link-event, and alarm-event evidence into a
deterministic operator inspection workflow while preserving the boundaries of each source format.

## Highlights

- `orbitops session inspect` produces bounded operator text or `orbitops.session_report/v1` JSON from
  any supported combination of telemetry, link-event, and alarm-event evidence.
- Source summaries, diagnostics, compatibility state, filters, timeline limits, and exit codes are
  explicit and deterministic.
- The flagship `make session-demo` workflow exercises the C++ thermal simulator, deterministic
  intermittent-loss link profile, ground station, alarm lifecycle, and unified inspector end to end.
- A small synthetic bundle under `examples/session-inspection/` provides a supported, human-reviewable
  inspection example.
- Raw reference benchmark and 60-minute soak evidence are retained in `docs/evidence/` with checksums
  and reproduction guidance.

## Compatibility

- The binary telemetry protocol and telemetry recording remain version `1`.
- Mission-profile and alarm-policy schemas remain version `1`.
- Link-event emission remains version `2`, with version-1 reading preserved.
- Alarm-event schema remains version `1`.
- Session reports begin at `orbitops.session_report/v1`.
- Telemetry/alarm exact correlation still requires a unique decoded packet-sequence match; link
  `packet_index` remains a separate namespace.
- Selecting multiple files for inspection does not prove cross-stream provenance.

## Validation and evidence

The release candidate is required to pass the repository's full `make verify` gate, supported Python
3.11–3.13 compatibility jobs, Linux/macOS C++ builds, sanitizer checks, package-resource checks, a
fresh installed-wheel session-inspection check, and the external usability walkthrough tracked in
`docs/release-readiness.md`.

The retained benchmark and soak results are environment-specific reference evidence. They are not a
performance SLA, a leak-free guarantee, a general reliability certification, or a cross-platform
performance claim.

## Supported environment

- Python 3.11–3.13;
- C++17;
- CMake 3.20 or newer;
- Linux and macOS for the supported CI/build paths.

## Known boundaries

OrbitOps remains technical-preview simulation software. UDP transport is unauthenticated and
unencrypted; CRC-32 and configuration fingerprints are not cryptographic authenticity or provenance
mechanisms. The project is not flight software, a safety-certified alarm system, an RF propagation
model, or a claim of CCSDS compliance.
